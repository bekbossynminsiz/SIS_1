SIS - Text Analyzer (Checkpoint 1)
A small synchronous, in-memory Go application. A task is a unit of work that analyzes a piece of text: given an input string, it calculates the number of words, the number of characters, and the longest word.

Example:

Input:  "Hello Go world"
Result: words = 3, characters = 14, longest word = "Hello"
Project structure

├── go.mod
├── main.go              # short demo of the application
└── task/
    ├── task.go          # Task model, statuses, errors, allowed transitions

    └── task_test.go     # unit tests
Domain model
Each Task contains:

Field	Type	Description
ID	int	Unique identifier, generated by the store
Text	string	Input data to analyze
Status	Status	Current lifecycle state
Result	*Result	Processing result; nil until the task is processed
Task lifecycle
Pending -> Processing -> Completed
                     \-> Failed
From	Allowed transitions
Pending	Processing
Processing	Completed, Failed
Completed	none (final state)
Failed	none (final state)
A new task is created as Pending.
When processing starts, the task becomes Processing.
If the analysis succeeds, the result is saved and the task becomes Completed.
If the processor returns an error, the task becomes Failed and has no result.
Any other transition is invalid and returns ErrInvalidTransition. For example, processing an already completed task again is rejected.
Input validation
Text that is empty or contains only whitespace (spaces, tabs, newlines) is rejected with ErrEmptyInput. Such a task is never created or stored.

Error handling
Expected application errors are returned as normal Go errors (no panic):

ErrEmptyInput - invalid input text
ErrTaskNotFound - no task with the requested ID
ErrInvalidTransition - invalid status change or operation
Errors are wrapped with %w to add context (for example the task ID) and can be checked with errors.Is.

Design decisions
Interface: Processor (Process(text string) (Result, error)) separates the storage and lifecycle logic from the processing logic. Store depends on the interface, so the analyzer can be replaced, and tests use a failing fake processor to check the Failed state.
Map storage: tasks are stored in map[int]*Task for fast lookup by ID. Pointers are used so that status and result changes are applied to the stored task itself rather than to a copy.
Unique IDs: the store keeps a nextID counter that increases with each created task.
Receivers: Task.transition uses a pointer receiver because it modifies the task. TextAnalyzer.Process uses a value receiver because the type has no state.
Characters: counted with utf8.RuneCountInString, so non-ASCII text (for example Cyrillic) is counted correctly, not by bytes.

Tests
Tests use the standard testing package and cover:

successful task creation
invalid input (table-driven)
successful retrieval and retrieval of a nonexistent task
successful processing, result correctness, and final status (table-driven)
invalid operation: processing a completed task again
processor failure leading to Failed status
allowed and forbidden status transitions (table-driven)
multiple independent tasks that do not mix or overwrite each other's data
